# Order source ingestion contract (v1)

`GET /exports/orders` returns UTF-8 newline-delimited JSON, one complete order per line. `?since=<ISO-8601 UTC timestamp>` filters to orders whose `updated_at` is greater than the supplied instant. Every record contains `order_id`, `customer_id`, `order_status`, `order_timestamp`, `currency`, `order_total`, `created_at`, `updated_at`, `source_version`, and a complete `items` array. Each item contains `order_item_id`, `product_id`, `quantity`, `unit_price`, `discount_amount`, and `line_total`.

Money is a decimal string with exactly two fractional digits, calculated and persisted as integer cents. Timestamps are UTC RFC3339/ISO-8601 strings with microsecond precision and `Z` suffix. IDs are strings. Order items are exported in stable ID order; full exports sort by `(order_timestamp, order_id)`, while changes sort by `(updated_at, order_id)`. List and changes endpoints paginate with offset/limit; export currently emits the complete matching result in one response.

For polling, persist a checkpoint only after the page is durably landed. The current `since` filter is strict `>` and ordering is deterministic, but timestamp polling can miss changes in failure/retry edge cases, and offset pagination can shift while records mutate. A consumer should poll with a small overlapping time window and upsert/deduplicate on `(order_id, source_version)`. `source_version` increments on each accepted update.

This is not full CDC: SQLite updates are not exposed as a durable ordered event stream, deletes are not represented, and equal/precision-boundary timestamps complicate checkpointing. A production evolution should add an append-only `order_changes` table written in the same transaction (or a transactional outbox), with monotonic sequence, operation type, changed record snapshot, and stable event ID. Consumers would then checkpoint sequence rather than wall-clock time. Large-scale export should add opaque cursor pagination or snapshot-based file generation.
